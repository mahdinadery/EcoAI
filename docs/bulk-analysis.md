# تحلیل انبوه (استفاده از ظرفیت توکن، بیرون از صف ترتیبی)

## چرا صفِ عادی کند به‌نظر می‌رسد

صف خودکار (`drainArticleQueue` در `src/lib/news/article-queue.ts`) عمداً
**ترتیبی و تک‌تک** است:

- مقالهٔ قدیمی‌تر باید اول تحلیل شود تا ترتیب ورود کانال حفظ بماند؛
- اگر تحلیلی خطا بدهد، صف **همان‌جا می‌ایستد** تا با تلاش‌های پیاپی ترتیب عوض نشود؛
- هر درخواست حداکثر ۲۴ مقاله و حداکثر ~۴۶ ثانیه وقت دارد (`maxDuration = 60` روی Render)؛
- در هر دور، بین دو تحلیل، ارسال‌های معوق هم تخلیه می‌شوند.

نتیجه: حتی وقتی سقف توکنِ API خالی است، نرخ تحلیل حدود ۱۰ مقاله در دقیقه می‌ماند.
«تحلیل انبوه» همان داده‌ها را با همان قوانینِ غیرصف‌ای (فیلتر موضوعی، قفل اتمی هر
مقاله، بریکر خطای Provider) اما **چندتا هم‌زمان و بدون ارسال** پردازش می‌کند.

## سه راه عملی

### ۱) دکمهٔ «تحلیل انبوه» در داشبورد (روزمره)

`/admin` → نوار ابزار «شتاب‌دهندهٔ ورود و ارسال مقالات» →
**«تحلیل انبوه صف — N مقاله هم‌زمان (بدون ارسال)»**.

- هر درخواست تا ۱۲۰ مقاله را تلاش می‌کند و پیش از پایان مهلت زمانی خودش برمی‌گردد؛
  کلکِ دکمه این درخواست‌ها را تا ۴۰ نوبت پشت‌سرهم می‌زند و بنر، نرخ دقیقه‌ای و
  باقی‌مانده را زنده نشان می‌دهد؛ «توقف تحلیل انبوه» بعد از آخرین موج قطع می‌کند.
- منوی «هم‌زمانی» تعداد درخواست‌های موازی AI را تعیین می‌کند (۲ تا ۸). اگر Provider
  شما خطای `429` می‌دهد، عدد را کم کنید؛ اگر نه، ۶ یا ۸ معمولاً بی‌خطر است.
- قطعِ ارتباط یا Restart سرور چیزی را خراب نمی‌کند: مقاله‌ای که نیمه‌کاره بماند،
  پس از ۹۰ ثانیه دوباره قابل تصاحب است و ادامهٔ صف از همان‌جا شروع می‌شود.

### ۲) برای رانِ بزرگ: GitHub Action

`Actions → «Bulk analyze backlog (tokens → analysis, no sending)» → Run workflow`
با ورودی‌های `total` (مثلاً ۵۰۰۰)، `per_request` (پیش‌فرض ۱۲۰) و `concurrency`.
چون از طریق خودِ اپلیکیشن اجرا می‌شود، به کلید دیتابیس یا دسترسی شبکه نیاز ندارد و
تا ۴۵ دقیقه می‌تواند ادامه یابد — مناسب روزی که انباشت چند هزار مقاله‌ای دارید.

### ۳) برای حالت خودکار: سقف هر نوبت

کارت «زمان‌بندی خودکار» → «حداکثر تحلیل در هر اجرا» (`maxAnalyze`، تا ۳۰). این عدد
را زیاد کنید اگر می‌خواهید تیک‌های ۵ دقیقه‌ای خودش تندتر پیش بروند؛ برای تخلیهٔ
یک‌بارهٔ انباشت، گزینهٔ ۱ یا ۲ مناسب‌تر است.

## رفتار و مرزها

| مورد | تحلیل انبوه |
|---|---|
| ارسال به بله/تلگرام | **هیچ**. ارسال‌ها را سیاست ارسال خودکار یا دکمهٔ «ارسال…» تعیین می‌کند، پس انباشتِ تحلیل‌شده هرگز خودبه‌خود به کانال نمی‌رود |
| فیلتر موضوعی | اعمال می‌شود؛ موارد غیرمرتبط مثل حالت عادی `SKIPPED_OFFTOPIC` می‌شوند (برگشت‌ناپذیر برای این صف، اما بی‌هزینه از نظر توکن) |
| قفل صف (advisory lock) | گرفته **نمی‌شود**؛ تیک‌های خودکارِ هر ۵ دقیقه به کارشان (تحلیل ترتیبی + ارسال) می‌رسند |
| تکرار تحلیل | ممکن نیست؛ هر مقاله با یک `UPDATE … claim` اتمی قفل می‌شود. اگر دو کارگر هم‌زمان یک ردیف را بردارند، بازنده `already_processing` می‌گیرد و در شمارش جداگانه گزارش می‌شود |
| خطای Provider | استخر هم‌زمانی روی خطای مجوز/سقف مدار را می‌بندد؛ درخواست با `stopReason: "budget_exhausted"` و `firstError` برمی‌گردد تا دوباره تلاش کنید |
| مقالات قدیمی/خارج از موضوع | مثل بقیهٔ مسیرهای دستی، بدون محدودیت سنی؛ `AUTO_SEND_MAX_AGE_DAYS` فقط به **ارسال** مربوط است، نه تحلیل |

پاسخ هر درخواست این فیلدها را دارد: `analyzed`, `failed`, `inFlight`,
`skippedOfftopic`, `attempted`, `target`, `concurrency`, `elapsedMs`, `firstError`,
`remainingReady` (فقط `READY_FOR_AI`، همان شمارۀ کارت) و `remainingQueue` (همۀ ردیف‌های
قابل تحلیل: `READY_FOR_AI` + `FETCHED` کنارگذاشته + `FAILED`)، به‌همراه `stopReason` با
مقادیر `target_reached` | `queue_empty` | `budget_exhausted` که به دکمهٔ توقف و به
Action می‌گوید کی باید بایستد.

## چقدر توکن مصرف می‌شود؟ (عدد واقعی، نه تخمین)

اپلیکیشن مصرف هر تحلیل را ثبت می‌کند:

```bash
curl -s https://<app-url>/api/news/stats | python3 -c 'import json,sys; d=json.load(sys.stdin); print(d["tokenUsage"])'
# {'totalTokens': …, 'promptTokens': …, 'completionTokens': …, 'todayTokens': …, 'analyzedCount': …}
```

پاسخ همین endpoint `analyzedCount` را هم برمی‌گرداند، پس میانگین توکن هر مقاله = `totalTokens ÷ analyzedCount` (بدون کوئری جدا). برای رانِ بزرگ،
`per_request` را چنان انتخاب کنید که `todayTokens` نزدیک سقف روزانهٔ Provider نشود؛
اگر به سقف بخورید، پاسخ با `firstError` مربوط برمی‌گردد و کار باقی‌مانده در صف
می‌ماند (چیزی گم نمی‌شود). همان جمع را در `/dashboard` هم می‌توانید ببینید.

## منطق قابل‌تست

مرزبندی‌ها در ماژول خالصِ `src/lib/news/bulk-analysis.ts` است (`clampBulkTarget`،
`clampBulkConcurrency`، `planBulkChunk`، `estimateItemMs`) و با
`tests/bulk-analysis.test.mjs` پوشش داده شده: هیچ درخواستی بیشتر از آن‌چه در زمان
باقی‌مانده جا می‌شود کار نمی‌گیرد، و سرعت واقعی موج‌های اول روی اندازهٔ موج‌های
بعدی اثر می‌گذارد (تا درخواست زودتر از مهلتِ میزبان تمام شود، نه اینکه کشته شود).
